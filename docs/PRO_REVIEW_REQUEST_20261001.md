# Forsic 조사 구조 재설계와 Jev 도입 완료를 위한 Pro 검토 요청

이 문서는 사건 원문·경로·호스트·계정·주소·인증정보를 제외한 코드 검토 질문서입니다.
소스는 이 문서와 같은 Git 커밋을 기준으로 읽어 주세요. 아래 수치는 2026-10-01
04:34~04:45 KST에 수행한 비식별 운영 감사의 요약이며 현재 순간의 실시간 상태는 아닙니다.
공개 저장소에는 실제 사건 DB와 모델 입출력 전문을 포함하지 않습니다.

## 사용자의 요구 — 검토의 전제

1. **최소 수정안이 목표가 아닙니다.** 조사 성능·비용·복구·설명 가능성을 개선하기 위해
   구조 변경, 모듈 통합·삭제, 역할 재배치, 데이터 흐름 재설계를 허용합니다. 현재 구조를
   유지하는 작은 패치로 한정하지 말고, 완성된 목표 구조와 실행 가능한 구현안을 제시해 주세요.
2. **이번 개편에서 Jev 도입을 완료해야 합니다.** 연결 시험·shadow·채택 후 분류 보조만으로
   완료 처리하지 않습니다. 일반 LLM 한 개와 Jev 한 개의 역할을 제품에서 설정하고,
   실제 조사 흐름과 사용자 설명에 연결하고, 유효성·실패 대응·효과 측정까지 구현하는 것이 목표입니다.
3. 근거가 부족한 확률을 진실·침해 확률로 표현하거나, 중요한 단서를 조용히 버리는 방식은
   원하지 않습니다. 이 제약 안에서 Jev를 실용적으로 적극 활용할 방안을 설계해 주세요.
4. 테스트 일반 LLM은 GPT-6 Luna, 운영 목표는 Qwen입니다. Jev는 기존 Ollama에 설치한
   `openjev-27b-nothink:latest`이며 upstream은 `openjev/openjev`입니다.
   Luna 시험 결과를 Qwen 운영 품질·성능 검증으로 대체하지 말아 주세요.

## 제품 목표

대형 디스크 이미지에서 단서를 찾고, 가능한 사건 설명과 정상 경쟁 설명을 세우고,
설명을 구별할 검사를 실행한 다음 결과에 따라 질문의 답을 갱신하는 로컬 포렌식 제품입니다.
추론과 가설 생성은 적극적으로 하되 관측·해석·확정을 구분해야 합니다.
모든 일을 안전하게 거부하는 것만으로는 제품의 목적을 달성할 수 없습니다.

사용자는 포식이라는 안내 캐릭터를 통해 다음을 이해하고 싶어 합니다.

> 무엇을 의심하는가? 왜 그렇게 보는가? 지금 무엇을 확인하는가?
> 결과가 어떻게 나오면 판단이 바뀌는가? 직전 시도에서 무엇을 알게 됐는가?

현재 화면은 중앙 캐릭터, 이전 결과·현재 작업 말풍선, 마지막 가설과 핵심 사건 시간축입니다.
내부 사고 전문이 아니라 채택된 근거, 검사 목적, 결과, 남은 공백을 설명해야 합니다.

- 질문·대상·소유자·버전·판별 조건을 보존하는 검사 계약과 엄격한 admission.

### Jev의 실제 도입 상태

분류 보조30건, 입력13,242/출력30토큰. 대상·출처·버전·요청 결속과 첫 출력의
네 후보 bytes/logprobs 저장을 확인했습니다. 현재는 차수당30건·60초 이상 간격,
`probabilities=null`, `policy_applied=false`, advisory 역할입니다.
중요 근거 제외·필수 검토 생략·새 작업·최종 판단·침해색에는 사용하지 않습니다.
현재처럼 채택 이후 분류에 머무는 상태는 **이번 개편의 Jev 도입 완료 기준에 못 미칩니다.**

배포 권리와 설치 artifact의 provenance는 실제 적용 환경에 맞춰 확인이 필요합니다.

## 요청 1 — 목표 조사 구조를 다시 설계해 주세요

입력 예산, 교정 반복, 종합 갱신 지연 중 어디가 원인인지 코드로 검토해 주세요.

권고 구조 하나와 선택 이유를 제시해 주세요. 신규 테이블·계층 추가만으로 답하지 말고
제거·통합할 기존 구조도 명시해 주세요.

## 요청 2 — 이번 개편에서 Jev 도입을 완료할 구현안을 제시해 주세요

일반 LLM 한 개와 Jev 한 개의 구체적인 역할을 확정하고 실제 데이터 흐름에 연결해 주세요.
다음 후보를 검토하되 더 적합한 역할이 있으면 제안해 주세요.

- 원문·단서 유형 분류와 질문 관련성 정렬.
- 검토할 근거 묶음 선택과 비슷한 요청의 묶음 후보 탐지.
- 검사 결과가 어느 조건을 판별할 수 있는지의 보조 분류.
- 불확실성·상충·추가 LLM 검토 필요성 탐지.
- UI의 설명 그룹·우선 표시·불확실성 시각화.

각 역할마다 입력, label 정의, readout 의미, 허용 행동, LLM과의 인계, 저장·정정,
예산, 실패·미지원 fallback, 실행할 때와 생략할 때, 평가 자료와 지표를 정의해 주세요.
점수가 없거나 잘못 보정돼도 근거가 사라지지 않아야 합니다. 보류·기권 및 유한 공정성을
포함하고, 모델 자신감과 근거의 실제 지지 정도를 구별해 주세요.

현재 `decision_*`/`openjev_readout` 코드에서 재사용·확장·폐기할 부분을 지정하고,
설정 UI와 실제 scheduler/평가/UI 설명까지 연결하는 순서를 제시해 주세요.
첫 단계 shadow 측정은 가능하지만 최종 산출물을 shadow에 남겨 두지 마세요.
출시까지 필요한 검증을 이번 구현 계획에 넣고, 검증 실패 시 완료를 허위 선언하지 않는
구체적 중단 조건을 정해 주세요. 역할별 품질 기준의 값은 근거 없이 만들지 말고
기준선·라벨링·보정·회수율 시험을 통해 고정하는 절차를 정의해 주세요.

동일 Ollama/GPU에서 두 모델을 운용할 때의 메모리·교체 비용·큐·backpressure도 설계해 주세요.
Jev 호출 자체가 LLM 절감 효과보다 비싸지는 경우를 측정하고 제어해야 합니다.
Qwen+Jev 운영 검증과 Luna+Jev 하네스 시험의 역할도 구분해 주세요.

## 요청 3 — 복구를 원래 조사 의무의 해결로 연결해 주세요

입력 초과, 원문 선택 실패, 질문·명제 참조 오류, 모델 의미 오류, 도구 부분 실패,

긴 원문을 충분히 보존하면서 질문별 필요한 구간과 판별 조건을 제공하는 방법,
결정론적 추출·검증/Jev/일반 LLM의 분담, 공통 스키마·과거 판단·feedback 비용 절감을
제안해 주세요. 처리량보다 반환→판별 지연, 질문의 답 변화, 미해결 의무,
실패 포함 비용을 기준으로 예산을 운영할 구체 정책이 필요합니다.

가설은 자유롭게 제안하고 경쟁 설명을 유지하되 무한 탐색·같은 검토 반복은 줄여야 합니다.
관측 수를 규명률로 쓰거나 정답 자료 없이 precision/recall을 산출하지 마세요.
검토할 가지의 우선순위와 설명의 근거 지지를 별개로 다뤄 주세요.

## 요청 5 — 사용자가 이해할 설명과 보고서까지 완성해 주세요

포식이의 이전 결과·현재 작업·가설·시간축이 같은 근거 버전으로 다음을 설명해야 합니다.
무엇을 확인했는지, 왜 확인하는지, 어떤 결과가 어느 설명을 바꾸는지, 실패로 무엇이 남았는지.
설명용 별도 LLM이 새로운 판단을 만들어 비용과 불일치를 늘리는 구조는 피하고 싶습니다.
동일 시각의 다른 기록은 구별하고, 같은 원문의 중복 표시는 합치되 출처·발생·재사용 관계는 보존해 주세요.
임원 요약과 분석가 상세 보고서가 실제로 읽을 수 있는 길이와 근거 탐색성을 갖춰야 합니다.

**직관적인 UI 배치도 이번 개편 범위입니다.** 기존 배치를 그대로 유지할 필요는 없습니다.
포식이, 현재 조사, 바로 이전 결과, 현재 가설과 이유, 핵심 사건 시간축, 전체 작업 이력,
근거 상세를 사용자가 어떤 순서로 읽어야 하는지부터 설계해 주세요. 기술적인 원장 용어와
진단 수치는 기본 화면을 압도하지 않게 하고, 실패·중요 정정·미확인 범위는 발견하기 쉬워야 합니다.

- 기본 데스크톱 화면의 구체적 와이어프레임과 영역별 크기·위치·읽는 순서.
- 기본 노출/접기/상세 팝업으로 보낼 정보, 한 화면에 동시에 보여줄 설명의 수.
- 현재 작업과 직전 결과의 시각적 연결, 가설 여러 개와 작업 이력의 탐색 방법.
- 하단 시간축의 핵심 문장·이유·근거 열기, 동일 시각의 다른 기록을 구별하는 표현.
- 조사 초기·검토 중·자료 대기·부분 실패·정정·완료 각각의 화면 예시 문구.
- 좁은 화면과 키보드 사용 시 레이아웃, 스크롤·선택·원문 열람 위치 보존.
- 현재 배치와 제안 배치의 장단점 및 사용자가 잘못 이해하는지 확인할 과제.

추상적인 '깔끔하게/사용자 친화적으로' 대신 실제 컴포넌트 배치·상태별 예시를 주세요.
포식이는 중앙의 안내자로 돋보이되 읽기 공간을 빼앗지 않게 하고, 회색 UI와 캐릭터의
상태 색·표정 역할을 구분해 주세요. 일하는 연출만으로 조사 진전이나 침해 확정을 암시하면 안 됩니다.
