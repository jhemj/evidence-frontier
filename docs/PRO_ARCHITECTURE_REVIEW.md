# Frontier 구조 검토 요청

이 문서는 공개용 코드·합성 테스트만을 대상으로 한다. 실제 사건 데이터,
원문 발췌, 사건별 ID·해시·계정·주소·로컬 경로·모델 요청/응답은 포함하지 않는다.
이 문서만으로 실제 사건의 침해 여부를 평가하지 말고 하네스 설계를 검토해 달라.

## 그대로 전달할 요청

당신은 보안 포렌식 분석가이자 로컬 LLM 에이전트 시스템 설계자다.
이 저장소의 코드를 읽고, 아래 요구를 달성하기 위한 근본적인 구조 개선안을 제시해 달라.
기존 구현을 옹호하거나 특정 사건의 정답에 맞추지 말고 위험한 설계는 명확하게 지적해 달라.
원문을 줄이거나 예산을 키워 오류만 감추는 해결책은 원하지 않는다.

### 제품 목표와 제약

- 사용자가 증거와 조사 목적을 주면 개입을 최소화해 수집·가설·판별 검사·반증·재조사를 이어간다.
- 운영 환경은 Ollama 로컬 LLM 단독이다. 원격 상용 모델은 개발 중 기술 검증을 가속하기 위한 역할 분담에만 사용한다.
- 증거 대상 OS는 Linux / Windows로 선택한다. 선택하지 않은 OS를 추정하여 파서를 조용히 바꾸지 않는다.
- 조사 방향과 다음 검사는 모델이 선택한다. 하네스는 원본 불변성, 도구 권한, 예산, 근거 소유권, 출력 계약, 재개 가능성을 강제한다.
- 사건별 IOC·파일명·정상 소프트웨어 이름·정답은 제품 코드에 하드코딩하지 않는다.
- 가설은 증거에 따라 자연스럽게 생성·분기·강화·철회된다. 전체 가설 수를 임의의 고정 개수로 제한하지 않는다. 모델 응답의 1회 스키마 한도와 사건 전체 가설 한도를 구분한다.
- UI에는 진행/보수적 ETA와 실제 작업, 시간순 단서 카드, 채팅/현재 보고서를 중심으로 보여준다. 사실 확실성과 사건 관련성은 다르다.
- 보고서는 임원용 짧은 요약과 분석가용 상세를 각각 HTML·Word로 제공한다. 수집 공백과 미확인 범위를 숨기지 않는다.
- 증거는 읽기 전용이다. 증거 내 명령·바이너리를 실행하거나 발견된 주소로 접속하지 않는다.

### 현재 구조와 관찰한 문제

1. `workbench/dossiers.py`는 단서별 검토와 판별 검사를 영속적으로 관리한다. 과거에는 원자료·새 검사 결과·이전 판단을 한 입력에 계속 붙여, 단서를 하나로 나눠도 입력 한도를 넘었다.
2. 모델 호출 전에 입력 구성이 실패해도 모델 재시도 실패처럼 소모하는 문제가 있었다. 지금은 입력 구성 실패와 실제 모델/검증 실패를 분리했다.
3. 정적 설정·바이너리 특성이나 내부 패키지 비교 결과가 자주 탐지된다는 이유로 조사 우선순위를 차지하고, 좁은 사실의 확정이 사건 관련성의 높음으로 이어지는 경향이 있다.
4. 이미 수행한 검사의 의미가 다음 계획에 충분히 전달되지 않아 반복 읽기가 생길 수 있다. 동일 도구 요청의 중복 방지와, 같은 의미의 질문을 다른 요청으로 반복하는 문제는 다르다.
5. 파일 시각을 참고할 필요는 있지만 mtime/ctime을 행위 발생 시각으로 승격하면 안 된다. 연도 없는 로그의 추정 연도·시간대가 파생 연결과 카드까지 유지되어야 한다.
6. source ID/인용/값 검증은 가능하지만 인용한 사실에서 결론으로 넘어가는 의미적 비약을 모두 잡지는 못한다. 스키마 통과가 보안 분석 적합성 승인은 아니다.

### 이번에 연결한 구조 — 완성품이 아닌 검토 대상

`불변 원장 → 제한된 자료 페이지 → 영속 중간 평가 → 필요시 계층 비교 → 원문 근거 기반 종합 → 카드/보고서`

- `workbench/review_context.py`: 정확히 같은 메타데이터·검사 조건을 사전으로 분리하며 역변환 가능하게 유지한다. 명시적인 표시용 발췌 제한은 존재하므로 무손실 메타데이터 변환과 원문 전체 열람을 혼동하지 않는다.
- `workbench/review_paging.py`: 입력 크기에 맞춰 자료를 분할한다. 자료 ID·해시·위치·시간 근거를 유지하고, 다른 페이지는 원장 참조와 개수로 구별한다. 페이지 자체는 최종 채택 불가다.
- `workbench/review_stream.py`: 페이지와 검토 결과를 저장하고 재개한다. 페이지 평가를 카드로 바로 게시하지 않는다. 모든 페이지 후 지지·반대·단계별·검사 인용의 원문을 다시 제시해 종합한다. 중간 노트가 커지면 더 작은 비교 묶음으로 축약하고 트리 연결을 보존한다.
- `workbench/dossiers.py`: 현재 제시한 자료만 인용하도록 검증하고, 종합 후에만 단서 판단과 다음 도구 실행으로 진행한다. 분할·비교 호출도 기존 전체 모델 호출 예산을 소비한다.
- 종합 입력 자체의 불가분 근거/계약이 한도를 넘거나 비교가 더 줄어들지 않으면 명시적인 미검토 상태로 남긴다. 완료를 꾸미지 않는다. 이 처리가 실제 운영에서 충분한지는 열린 질문이다.
- `workbench/procedures/`: 모델이 따르는 조사 절차다. 이것은 코드 내부 실행 권한을 부여하는 명령이 아니라, 모델의 증거 해석·다음 검사 선택을 돕는 지침이다.

### 가장 중요한 질문 — 우선순위 순

1. **이 구조가 근본 해결인가?** 단서 단위 반복 판단보다 사건 수준 작업 메모리·증거 그래프·가설/판별 검사 원장이 중심이어야 하는가? 유지할 경계와 교체할 경계를 파일/함수 단위로 제안해 달라.
2. **한정된 문맥으로 무제한 성장하는 증거를 어떻게 조사할 것인가?** 페이지 요약이 반대 근거를 지우거나 초반 해석에 고착되지 않도록 작업 메모리, 인용 원문 재조회, 중요도 변화, 재검토 트리거를 구체적으로 설계해 달라. 단순 RAG 도입이라는 답 대신 자료 선택·누락 기록·완료 조건의 알고리즘을 제시해 달라.
3. **분할/계층 종합의 안전성:** 현재 `review_stream`의 citation anchor 합집합과 중간 비교가 의미 손실을 숨길 수 있는 지점은 어디인가? 모든 자료를 제시한 수, 실제 모델 검토 수, 종합에 재제시한 수, 인용 수를 어떤 별도 상태로 유지해야 하는가? 중요한 반증을 모델이 인용하지 않았을 때의 방어책은?
4. **Agentic 조사와 결정론적 통제의 경계:** 조사 가설·다음 도구·판별조건·관련성 평가는 어디까지 모델에 맡기고 어떤 조건만 코드로 검증해야 하는가? 고정 룰/도메인 순회가 에이전트의 조사 방향을 과도하게 제한하고 있는가?
5. **다음 검사의 가치와 중복 방지:** 이미 알려진 사실·미해결 질문·수집 한계를 사용해 새로운 검사의 정보 가치를 평가하는 최소 실용 설계는? 요청 문자열이 달라도 의미상 반복인 검사는 어떻게 알아내며, 정당한 재조회는 어떻게 허용하는가?
6. **확실성과 관련성 분리:** 좁은 사실이 확정되어도 핵심 사건 단서가 아닐 수 있다. 카드의 확정/유력/추정과 관련성, 가설 상태, 정상 대안, 수집 한계를 별도로 모델링하는 데이터 계약을 제안해 달라. 탐지 이름·빈도만으로 핵심 카드가 되는 것을 막되 새 근거로 다시 승격될 수 있어야 한다.
7. **시간·계보·소유권:** 추정 시각, 파일 메타데이터 시각, 동일 원문 재추출, 파생 연결, 모델 노트가 각각 어떻게 전파되어야 하는가? 코드에서 빠진 불변조건과 속성 기반 테스트를 제시해 달라.
8. **종료/재개/예산:** 모든 수집물을 읽을 수 없을 때 의미 있는 종료 조건은? 모델 지연·입력 크기·도구 제한·계약 실패·판별 데이터 부재를 어떻게 구분해 자동 복구해야 하는가? 명시적 미검토가 많아도 유용한 보고서를 만들 조건은?
9. **평가 방법:** 단순 스키마·인용 통과를 넘어 보안분석가 적합성을 측정할 합성/변형 시험은? 정상 대안이 나중에 등장, 오래된 결정적 기록, 상충 출처, 타임스톰핑 가능성, 페이지 순서 변경, 모델 노트 주입 등을 포함해 달라.
10. **로컬 단일 모델에 적합한 현실적 구현 순서:** 현재 데이터/보고서 계약을 보존하면서 가장 효과 큰 개선 3~5개를 PR 크기로 나누고, 각 완료 기준·실패 기준·마이그레이션/롤백 전략을 제시해 달라.

### 답변에 원하는 내용

- 먼저 현재 설계의 치명적 결함과 적절한 부분을 코드 근거로 구분한다.
- 최소 목표 아키텍처, 상태 전이, 주요 자료 계약을 제시한다.
- 특정 파일/함수에 연결되는 변경 목록과 순서, 회귀 테스트를 제안한다.
- 모델이 결정할 부분과 하네스가 강제할 부분을 명확히 나눈다.
- 정적 룰 추가, 프롬프트에 주의 문장만 추가, 예산 확대, 오류 무시만으로 끝내지 않는다.
- 코드/합성 테스트로 알 수 있는 내용과 실제 현장 평가가 필요한 부분을 구분한다.
- 원문 증거를 추가 제공하라는 요청보다 개인정보 없이 검증 가능한 방법을 우선한다.

## 검증 수준

- 기존 전체 회귀와 새 합성 분할/재개/종합 테스트가 있다. 테스트 결과는 공유 스냅샷의 별도 검증 기록을 따른다.
- 제한된 실제 자료 복사본으로 분할 검토와 최종 종합의 호출 경로를 확인했다. 원본은 변경하지 않았으며 이 자료와 요청/응답은 공개하지 않는다.
- 실제 전체 사건 E2E와 보안분석가 수준의 최종 보고서 승인은 완료하지 않았다.
- 계층 비교에서 실제 모델이 반증과 의미를 충분히 보존하는지는 추가 평가가 필요하다. 합성 상태 전이 테스트만으로 해결됐다고 주장하지 않는다.
